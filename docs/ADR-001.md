# ADR-001 · Elección del framework backend: FastAPI sobre Flask y Django

Estado: Adoptado   Fecha: 2026-09-25

## Contexto

El proyecto es un monolito modular organizado por dominio (órdenes de trabajo, historial, inventario, alertas, comparación, reportes, asistente IA). La pila está fijada por el steering tech.md: Python 3.11+, SQLite, datos simulados, Gemini API con clave en variable de entorno. El equipo es de cuatro personas, el plazo es de diez semanas y la mayoría no tiene experiencia previa con frameworks web Python. El diseño exige un servidor ASGI que pueda:
- Servir archivos estáticos (frontend HTML + JS) desde el mismo proceso.
- Exponer una API REST con validación automática de esquemas (Pydantic).
- Integrarse con el Servidor MCP de solo lectura vía cliente HTTP asíncrono.
- Verificar la presencia de `GEMINI_API_KEY` al arrancar y terminar el proceso con código distinto de cero si falta (Requisito 8.3).

Gobiernan esta decisión: la restricción de plazo y equipo (Alta), la mantenibilidad (módulos sustituibles para la Unidad 3, Alta), la fiabilidad ante caídas del MCP (Requisitos 2.4, 3.6, 4.6, 5.5, 6.6, Alta) y la confidencialidad de la clave de API (Requisito 8.1, Alta).

**Tensión declarada:** Django incluye más baterías (ORM, admin, auth) pero su curva de aprendizaje y su peso son innecesarios para seis funciones sobre SQLite. Flask es más liviano pero carece de validación automática de esquemas y documentación OpenAPI integradas, que reducen la carga del equipo para los contratos de API.

## Alternativas consideradas

### 1. Flask (versión estable vigente)

- *Ventajas:* curva mínima, ecosistema maduro, fácil de aprender en pocas sesiones.
- *Desventajas:* sin validación de esquemas integrada (se necesita marshmallow o wtforms aparte); sin servidor ASGI nativo (Werkzeug es WSGI); la documentación OpenAPI requiere extensiones de terceros. La carga de integrar cada pieza por separado supera el beneficio de la simplicidad inicial.
- *Instalación:* `pip install flask` [VERIFICAR versión mínima compatible con Python 3.11].

### 2. Django + Django REST Framework (versión estable vigente)

- *Ventajas:* ORM maduro, admin incluido, paquetes de auth robustos.
- *Desventajas:* exceso de abstracción para seis funciones sobre un solo archivo SQLite; las migraciones, el ORM y la estructura de proyecto de Django obligan a capas que el principio de diseño del steering ("sin sobreingeniería") rechaza explícitamente. La curva en ocho semanas para un equipo nuevo es alta. El admin y el ORM quedarían sin uso.
- *Instalación:* `pip install django djangorestframework` [VERIFICAR versiones compatibles].

### 3. FastAPI (versión estable vigente)

- *Ventajas:* ASGI nativo (compatible con uvicorn); validación automática con Pydantic v2; documentación OpenAPI generada sin configuración; montaje de archivos estáticos integrado (`StaticFiles`); soporte async para el cliente HTTP del MCP; ciclo de arranque (`lifespan`) para verificar variables de entorno antes de aceptar tráfico; generación de código predecible con Kiro. La organización por routers (`APIRouter`) se alinea directamente con los módulos de dominio del diseño.
- *Desventajas:* el equipo puede necesitar rampear en async/await; la documentación en español es menor que la de Flask o Django.
- *Instalación:* `pip install fastapi uvicorn[standard]` [VERIFICAR versión mínima de FastAPI compatible con Pydantic v2 y Python 3.11].

## Decisión

Se adopta **FastAPI** en su versión estable vigente con Pydantic v2, servido por **uvicorn**.

## Consecuencias

- *Positivas:* validación de campos obligatorios de OT (Requisito 1.3, 1.4) y de parámetros de búsqueda (Requisitos 2.5, 3.7, 6.4) se implementa declarativamente en los modelos Pydantic, sin código manual de validación. El ciclo `lifespan` de FastAPI permite verificar `GEMINI_API_KEY` al arrancar (Requisito 8.3). Los `APIRouter` por módulo refuerzan la frontera de dominio exigida por ADR-002.
- *Negativas:* el equipo debe familiarizarse con async/await para el cliente del MCP. El código generado por Kiro puede mezclar sintaxis de versiones de Pydantic [SUPUESTO]; requiere revisión.
- *Deuda técnica aceptada:* sin autenticación (el rol se elige en la UI — ADR-002). Sin paginación implementada más allá del límite fijo de 100 OT en historial.

## Criterio de reversión

Antes de la semana 7, se cambia a Flask si se observa cualquiera de estas evidencias:

1. El corte vertical H1→H2 (crear una OT y verla en el historial) no pasa sus pruebas al cierre de la semana 3.
2. Más de la mitad del código generado por Kiro requiere corregir errores de versión de Pydantic o de sintaxis async.
3. La instalación de `uvicorn[standard]` falla en alguno de los cuatro equipos tras un día de trabajo.
