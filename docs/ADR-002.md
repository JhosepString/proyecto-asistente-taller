# ADR-002 · Acceso a datos: lecturas por el Servidor_MCP de solo lectura, escrituras por un repositorio propio en cada módulo

Estado: Propuesto   Fecha: 2026-10-02

## Contexto

PA-01 eligió un monolito modular por dominio (órdenes de trabajo, inventario y alertas, reportes, asistente de IA y trazabilidad) con renderizado en servidor. Esta decisión la gobiernan R-2 (MCP de la semana 4 exclusivamente de solo lectura, Alta), QA-1 (95 % de consultas en 5 s, Alta) y QA-2 (mensaje de "servicio no disponible" si el MCP falla, Alta). También pesan R-4 y K-1 (plazo, equipo de cuatro y Python nuevo) y K-2 (el MCP puede no cubrir todas las consultas, o haber bloqueos por acceso compartido a SQLite).

**Tensión declarada:** H1, H5 y RNF4 necesitan escribir datos y el MCP no puede. No se resuelve ampliando el MCP.

## Alternativas consideradas

### 1. Ampliar el Servidor_MCP con herramientas de escritura

- *Ventajas:* un solo punto de acceso a la base.
- *Desventajas:* rompe R-2. Obliga a reabrir el servidor de la semana 4 en pleno plazo. Una caída del MCP bloquearía también el registro de OT (H1).
- *Instalación:* Python 3.11+ aparte (XAMPP no lo incluye), FastAPI y SDK de MCP [VERIFICAR versiones con el servidor de la semana 4].

### 2. FastAPI lee y escribe directo en SQLite; el MCP queda solo para el asistente

- *Ventajas:* la opción más simple y conocida (capas + SQL). Sin salto extra, lo que ayuda a QA-1.
- *Desventajas:* contradice los Req. 2.4, 3.6, 4.6, 5.5 y 6.6, que presuponen consultar vía MCP. Deja sin uso el MCP de la semana 4 en H2 a H6. Duplica la lógica de consulta.
- *Instalación:* Python 3.11+ aparte. El módulo `sqlite3` viene con Python [VERIFICAR].

### 3. Dos caminos por módulo: lectura por `McpReadClient`, escritura por repositorio SQLite propio

- *Ventajas:* respeta R-2. H1 funciona con el MCP caído. El "servicio no disponible" aplica solo a lecturas. Cada módulo declara qué lee y qué escribe, así que la regla se audita revisando que solo los repositorios contengan `INSERT` y `UPDATE`.
- *Desventajas:* dos accesos a la misma base. Hay que probar que una OT recién creada aparezca en la siguiente consulta. El salto FastAPI → MCP → SQLite agrega latencia.
- *Instalación:* Python 3.11+ aparte, dependencias de FastAPI y del SDK de MCP [VERIFICAR].

## Decisión

Se adopta la alternativa 3. Las lecturas (H2 a H6) pasan por `McpReadClient`; las escrituras (OT, conteo físico) pasan por el repositorio de escritura del módulo correspondiente. El registro de trazabilidad se rige por el ADR-003.

## Consecuencias

- *Positivas:* cumple R-2 sin tocar el MCP. El registro de OT no depende del MCP. El fallo del MCP queda acotado a las consultas.
- *Negativas:* hay dos caminos que mantener. Existe riesgo de bloqueo o de lectura desactualizada entre los procesos de FastAPI y del MCP sobre el mismo archivo SQLite [VERIFICAR modo de journal y apertura de solo lectura con una prueba; no configurar sin probar].
- *Deuda técnica aceptada:* no hay flujo de movimientos de stock (SIN TRAZA; ningún requisito define cómo cambia). Las alertas se recalculan en cada carga del panel y no dejan historial. El rol se elige en la interfaz, sin autenticación.

## Criterio de reversión

Antes de la semana 7, con 100 consultas simuladas de historial y stock, se pasa a un módulo de consulta directo con la misma interfaz (el MCP queda para el asistente) si se observa cualquiera de estas evidencias:

1. El p95 supera 5 s y la medición atribuye el exceso al salto por MCP.
2. La prueba "crear una OT y buscarla por placa de inmediato" falla o produce bloqueos reproducibles de la base.
3. Alguna consulta de H2 a H6 no se puede resolver contra el MCP (K-2).
